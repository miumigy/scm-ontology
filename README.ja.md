# SCM Ontology

> **サプライチェーン・マネジメント（SCM）のための、特定の業界・企業・ERP・WMS・TMS・計画製品などに依存しない意味モデルです。企業の根拠情報を共通の意味で扱い、基準情報、基準グラフ、推論、そしてSCM OSへつなげることを目的とします。**

[![CI](https://github.com/miumigy/scm-ontology/actions/workflows/ontology.yml/badge.svg)](https://github.com/miumigy/scm-ontology/actions)

**[English](./README.md) | 日本語**

## なぜSCM Ontologyなのか

企業のSCMデータは豊富ですが、ERP、WMS、TMS、APS、計画、物流、調達、製造、分析などのシステムごとに、識別子、意味、時間の扱い、前提条件が異なります。

そのため、システム間のデータをつないでも、**「そのデータがSCM上で何を意味するのか」**が統一されないまま、個別システムの意味が事実上の正解になってしまいます。

SCM Ontologyは、この問題に対して、企業システムの表現とSCM上の共通の意味の間に**意味統制の境界**を置きます。

中心となる考え方は次の一文です。

> **基準情報は、明示的な統治と判断を経て成立する。対応付け、推論、投影、集計、取り込みが成功しただけで、基準情報にしてはいけない。**

## SCM Ontologyとは

SCM Ontologyは、SCMを構成する基本的な対象、関係、出来事、状態、制約、意思決定、KPI、リスクなどを、特定ベンダーの製品用語とは切り離して定義する**基準意味モデル**です。

企業システムから得られた情報は、この基準意味モデルへ対応付けることができます。ただし、対応付けの結果は、統治された適用が行われるまでは、根拠情報を伴う結果として扱われます。

```text
企業システムの情報
    ↓
情報源・根拠・出所を保持
    ↓
対応付け・品質確認・識別
    ↓
基準意味モデル
    ↓
基準情報 / 基準グラフ
    ↓
問い・推論・投影
```

## SCM OSとは

SCM OSは、SCM Ontologyの上に構築される**統治された運用レイヤー**です。

状態を観測し、意思決定を組み立て、推論やシミュレーションを行い、提案を検証し、承認し、実行し、その結果を記録して次の意思決定につなげます。

```text
観測
 ↓
意思決定の文脈
 ↓
推論・分析
 ↓
提案
 ↓
検証
 ↓
承認・統治
 ↓
実行
 ↓
結果・監査・再現
 ↓
次の意思決定
```

AIやエージェントは、この仕組みの中で**推論や提案を行う役割**を担います。SCM OSの状態を勝手に変更する権限を持つものではありません。

## 一次公開：v0.1.0

**SCM Ontology v0.1.0 / SCM OS Reference v0.1.0** を、最初の公開リファレンス実装として位置付けます。

一次公開の目的は、すべての企業システムを本番接続することではありません。

> **SCMの意味を統一するための考え方と、それを守りながら動作するリファレンス実装を、第三者が理解・実行・拡張できる状態にすること。**

### 5分で理解 → 10分で実行 → 30分で拡張

一次公開では、内部の多数の開発番号を追うのではなく、1本の標準実行経路を入口にします。

```text
基準グラフを読み込む
→ SCM上の問いを立てる
→ 例外を確認する
→ 統治された意思決定を作る
→ 根拠・理由を確認する
→ 代替案をシミュレーションする
→ 承認する
→ 副作用のない実行を行う
→ 業務ワークフローを確認する
→ 監査・再現を確認する
→ エージェントによる限定された提案を見る
```

実行：

```bash
PYTHONPATH=src python -m scm_ontology.primary_launch --self-check
```

結果をJSONで確認：

```bash
PYTHONPATH=src python -m scm_ontology.primary_launch --json
```

## 複数システムをまたぐ具体例

ERP・WMS・TMSに相当する3種類の情報源を使った、決定的なリファレンス例を用意しています。

```bash
PYTHONPATH=src python examples/primary_launch_demo.py
```

この例では、

- ERPのCSV形式データ
- WMSのJSON形式データ
- TMSのSQL形式を想定したデータ

を、品質確認、対応付け、識別処理を経て、1つの**基準グラフではなく「参照用の統合結果」**へ収束させます。

特に、ERPとWMSの商品情報が明示的な識別情報によって同じ商品として対応付けられ、TMSの出荷情報がその商品との関係を持つ、というSCM上の意味を確認できます。

この例は**外部システムへ接続せず、外部への副作用も発生させません**。

詳細：[`docs/launch/demo.md`](docs/launch/demo.md)

一次公開では、単にテストが通るだけではなく、SCMの意味と統治上の境界が守られていることを確認します。

```bash
PYTHONPATH=src python -m scm_ontology.validator
```

主な確認項目は、

- アーキテクチャの一貫性
- 標準実行経路の実行可能性
- 複数情報源の統合例
- 基準情報の変更境界
- 出所・根拠情報
- 承認・統治
- 実行の安全性
- AI / エージェントの安全性
- 監査・再現性
- 公開ドキュメント
- CIによる自動検証

です。

詳細：[`docs/launch/acceptance.md`](docs/launch/acceptance.md)

## 一次公開で「主張しない」こと

v0.1.0はリファレンス実装です。以下を提供済みだとは主張しません。

- SAP / ERP / WMS / TMS / APSの汎用本番コネクタ群
- 本番環境の高可用性、SLA、災害復旧保証
- マルチテナントSaaSや企業向け認証・セキュリティ認証
- 本番規模のグラフ性能・運用保証
- 制約のない自律実行
- 推論・集計・投影・取り込みに成功しただけで基準情報になる仕組み
- APS、Optimizer、Schedulerなどの本番製品の代替

これらは弱点ではなく、**一次公開で何を実証しているのかを明確にするための境界**です。

詳細：[`docs/launch/limitations.md`](docs/launch/limitations.md)

## 基準情報を守るための基本原則

1. **基準情報を暗黙に変更しない** — 対応付け、推論、照会、投影、集計、再現などによって基準情報を勝手に変更しません。
2. **基準情報と派生結果を区別する** — 推論結果、集計結果、推奨、投影結果などを基準情報と混同しません。
3. **出所と根拠を残す** — どこから得られ、どの情報を根拠にした結果なのかを追跡できるようにします。
4. **履歴を残す** — バージョン、状態遷移、競合、解決、実行、結果を再構築できるようにします。
5. **不確実性を隠さない** — 未解決、競合、古い、部分的、失敗、不明などの状態を観測可能にします。
6. **承認を明示する** — 意思決定と実行の境界を明確にします。
7. **範囲を勝手に広げない** — 企業、組織、商品、期間などの適用範囲を暗黙に拡張しません。
8. **ベンダー固有の意味を基準モデルへ持ち込まない** — 必要な場合は明示的に管理・版管理します。
